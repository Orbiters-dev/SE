## 1. 인플루언서 수신자 식별 떠넘김 (재발)

**상황**: 岡山様 (はるくんママ) DM 본문에 「赤ちゃん相談室」(채널 컨셉) + 「30日の投稿予定」(어제 5/18 협의일) + 「22日(金)台本」(스케줄) 3개 단서. 단순 grep 「赤ちゃん相談室」 한 번 못 찾자 「누구인지 알려주세요」 객관식 떠넘김.

**세은 톤**: 「야 생각을 해」 → 「생각해서 처 아는 거 나한테 물어보지마」 (2단계 격화).

**진짜 path**: session_20260518.md 한 번만 정독했으면 #4 岡山様 매칭 자명. 단서가 3개 박혀있는데 도구 한 번에 매달려서 「확인 못 함」 결론낸 게 사고 근원.

**룰**: DM 본문 단서 3개 + 어제·그저께 세션 메모리 있으면 자체 식별 디폴트. `feedback_self_first_no_wongi_default.md` 5/19 케이스 박음.

## 2. 메모리 「~확인 + ~답신 대기」 반사 해석 (가이드라인 재발송 직전 정지)

**상황**: おとちゃんママ様 5/18 메모리 「가이드라인 확인 + 월령 답신 대기」를 「우리가 가이드라인 발송 + 월령 확인」으로 잘못 해석. STEP 2 PPSU 소개 + 가이드라인 재발송 답신 작성. 세은 「가이드라인은 벌써 다 보냈다 임마 기억 안 하냐? 디질라고」 강한 교정.

**진짜 해석**: 「가이드라인 확인」 주체 = 인플루언서. 「월령 답신」 주체 = 인플루언서. 우리가 보낸 가이드라인 + 월령 요청 메시지에 대한 인플루언서 답변 대기 상태였음.

**룰**: 메모리 다음 액션 표현 「~확인 + ~답신 대기」의 주체가 우리/인플루언서 어느 쪽인지 진행 이력 표 끝줄 STEP 으로 역추적. `feedback_memory_read_carefully_not_reflexive.md` 박음.

## 3. 워크플로우 dead rule 텍스트 그대로 따라감 (振込先 보강 시도)

**상황**: 野田 STEP 6 풀네임+이메일 수령 후, 워크플로우 STEP 6 「※有償の場合は以下も追加で収集する：報酬振込先」 라인을 보고 振込先 보강 라인을 DM 답신에 추가. 세은 「템플릿대로 처 하라고 니 맘대로 지랄떨지 말고」 강한 교정.

**진짜 운영**: 振込先은 계약서 DOCX 내 placeholder. 인플루언서가 DocuSeal 서명 시 직접 기입. DM 으로 묻기 X. 워크플로우 STEP 6 의 「※有償の場合は振込先 추가」 라인은 사실상 dead rule (실제 운영에서 미사용).

**자기교정 사고**: 첫 교정 받고 「振込先은 처음 묻지 마 / 별도 단계」 메모리 만든 후 振込先 라인 빼고 두번째 답신. 세은 「그거 받는 걸 언제부터 했는데」 화 — 「언제부터」 = 振込先 받기 자체가 우리 흐름엔 없음. 새 메모리 즉시 삭제 + 워크플로우 dead rule 라인 제거.

**룰**: `feedback_furikomi_inside_contract_not_dm.md` 박음. 워크플로우 STEP 6 + 契約書 概要 라인 정리 완료.

## 4. 단계 명확화 안 하고 갈팡질팡

**상황**: 振込先 라인 넣는 답신 ↔ 빼는 답신 갈팡질팡. 세은 「야 니 지금 단계에서 템플릿 읊어봐 아 또 뒤질라고」.

**진짜 단계**: STEP 6 정보 수령 → 계약서 작성 + DocuSeal 발송 → STEP 6.5 (送付 완료 통지 DM). STEP 6.5 표준 템플릿 그대로 사용.

**룰**: 한 사건에서 모순된 두 답신 만들기 X. 다음 단계 = 워크플로우 어디 STEP 인지 먼저 명확히.

**상황**: 振込先 관련해서 첫 교정 받고 「振込先 = 별도 단계 / 처음 묻기 X」 메모리 만듦. 두번째 교정에서 「振込先 받기 자체가 없음」 발견 → 메모리 삭제 + MEMORY.md 인덱스 롤백.

**원인**: 첫 교정의 진짜 의미 (워크플로우 라인이 dead rule이라 따르지 마) 를 「振込先 받는 시점이 다르다」 로 좁게 해석.

**룰**: 교정 받고 메모리 만들 때, 「세은의 발화 진짜 의미는?」 다시 한 번 확인. 표면 텍스트만 따라가서 좁은 룰 만들면 다음 교정 때 또 깨짐.
