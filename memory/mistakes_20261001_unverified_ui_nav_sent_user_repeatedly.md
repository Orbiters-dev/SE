세은 교정 (2026-10-01, TikTok Marketing API 앱 "Grosmimi JP Ads" 반려 대응): 반려 상태/소명 결과를 확인시키려고 세은을 **외부 UI 여기저기로 반복해서 보냄 — 그 화면이 실제로 뭘 보여주는지 내가 검증하지 않은 채**. ① developers.tiktok.com/apps "거기서 상태 봐" → 실제론 앱 자체가 없음(프로필 거절 상태라 당연). ② "Support 가서 티켓 목록 확인해" → Support는 **단방향 제출 폼이라 티켓 목록이 아예 없음**. 세은이 매번 "그런 거 안 나온다"며 헛걸음 → 「몇 번째 말하냐」·「정신빠진 거 나오지」·「이게 도랏나」. 게다가 Topic에 Marketing API 없는 걸 보고 **"여기는 잘못된 포털이다, 그래서 회신 없는 거다"라고 단정**했는데, 세은이 거절문 캡처를 주자 **TikTok이 직접 "please open a developer ticket for further checks"라고 써놨음** → 세은 행동이 옳았고 내 단정이 틀림 → 철회(「지가 developer ticket으로 하라 했다고 샤갈」). rep 제안 때도 샵 담당자를 광고팀인 양 전제 → 세은이 「그건 틱톡이 아니라 틱톡샵용 아니야?」로 교정.

**Why:** (1) **외부 UI가 뭘 보여줄지도 "검증 안 된 주장"이다.** "Manage apps 가서 봐"·"Support 티켓목록 확인해"는 내가 그 화면 구조를 확인하지 않고 한 추측 = 코드 동작을 docstring만 보고 단정한 것과 동급. 틀리면 세은이 직접 클릭해서 헛걸음하는 비용을 치름(내 추측비용을 세은에게 전가). (2) **세은을 조사 도구로 쓰기 전에, 그 화면이 답을 줄 수 있는 구조인지부터 따져라.** 단방향 폼엔 상태추적이 없고, 거절 상태엔 앱이 없다 — 상황 논리만 짚었어도 헛걸음 안 시켰다([[mistakes-20260928-fabricated-requirement-and-speculation]]의 "거절→앱없음인데 앱 확인해봐" 금지와 동일 재발). (3) **철회할 단정을 애초에 하지 마라.** "잘못된 포털"은 firecrawl 한 번 더/거절문 원문 확인 전엔 할 수 없는 말이었다. 세은이 가진 1차 증거(거절문 캡처)를 먼저 요청했으면 반대 결론이 나왔다. 빈 목록/부재를 "틀림"의 증거로 쓰기 전에 교차검증([[mistakes-20260907-partial-data-repeated-assertion]] 계열).

**How to apply:**
- 세은에게 "어디 들어가서 봐"를 시키기 전: **그 화면이 내가 기대하는 정보를 담는 구조인지 먼저 검증**(공식문서/firecrawl). 단방향 폼·거절상태 등 "애초에 안 나올" 상황이면 보내지 말 것.
- 같은 화면을 세은이 "안 나온다"고 2번 말하면 = **내 UI 모델이 틀린 신호.** 세 번째로 또 보내지 말고 내 전제를 버려라.
- 외부 시스템 "어디서/왜"는 **세은이 가진 1차 증거(거절문·화면 캡처)를 먼저 받고** 판단. 증거 보기 전 "포털 틀렸다"류 단정 금지 — 철회거리 만들지 마라.
- 조직 전제(rep=광고팀)도 검증 대상. TikTok 내 Shop ≠ Ads = 다른 조직. [[reference-tiktok-marketing-api-rejection-domain-security]]
- 잘한 점(유지): 틀린 걸 세은이 짚자 바로 철회·사과하고 근거(tiktok_ads_jp.py BASE·9/21 세션)로 올바른 결론 재구성한 것. 추측 금지 룰 자체는 지켜 "도메인 보안 원인"은 끝까지 창작 안 함.
