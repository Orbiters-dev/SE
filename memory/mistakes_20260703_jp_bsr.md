# 오답노트 2026-07-03~06 (JP Amazon/Rakuten BSR 시트)

여러 날 이어진 세션. 좌절·강한 교정 다수. 핵심 4패턴:

**1. 작업 전제(소스·방법) 모르면 추측 재구성 말고 먼저 확인.**
US 시트가 **Helium 10 Xray extension**으로 만든 건데, 나는 "Keepa product API / orbiters DK 파이프라인"으로 멋대로 단정하고 그 전제로 여러 턴 삽질(Keepa domain=5, orbiters cap, EC2 파이프라인 확장…). 세은이 "이거 us는 헬륨10 extension으로 긁으신 거래"라고 알려줘서야 방향 잡음.
**Why:** 산출물 재현 요청이면 "이거 원래 어떻게 만들었어?"를 **먼저** 확인. 소스 모른 채 도구 스택 역추론 = 시간 낭비.
**How to apply:** 남의 산출물 복제 = 제작 도구/방법 확인이 1번. 코드/API 역설계는 그 다음.

**2. 선택지 나열·"진행할까?" 반복 금지 — 결과나 명확한 설명 먼저.**
"A안/B안", "이대로 갈까?", "진행할까?"를 매 턴 던져서 「뭘 진행한다는 거???」 「어쩌라고」 「지랄 떨어」. 특히 "브랜드 dedup 하면 통일됨" 하고 **왜 통일되는지 로직을 안 보여주고** 진행 여부만 물음 → 「그렇게 하면 어떻게 통일이 되는데?」.
**Why:** 세은은 판단 근거·결과물을 원하지 객관식을 원치 않음. 결정 못 할 땐 실행해서 보여주고 고치는 게 나음. [[feedback_no_plan_narration_just_act]] [[feedback_objective_judgment_no_sway]] 재위반.
**How to apply:** 확인이 꼭 필요한 정책/틀만 1개 질문. 나머지는 만들어서 보여줌.

**3. 휴리스틱을 검증된 것처럼 단정 X.**
라쿠텐 제품 dedup을 **제목 키워드 규칙**으로 하고 "distinct 37종"이라 냄 → 「진짜 같은 제품으로 확인한 거 맞아? 뭘 기준으로 확인했어?」. 실제 #35·36은 스텐보틀인데 straw로 오분류. JAN/型番/製品ID 다 부재라 하드 확정 불가였음.
**Why:** [[feedback_verify_data_values_before_discussing]] 재위반. 추정 분류엔 "제목 기반 추정, 확정 아님" 라벨 필수.
**How to apply:** 근거(무엇으로 대조했나) 먼저 밝히고 수치 냄. 하드키 없으면 "없음" 명시.

**4. 메커니즘 동일하면 "추가 필요" 과장 X — 못하는 진짜 이유만 + 할 수 있는 최선 즉시.**
JP도 US랑 같은 "아마존 스크랩" 메커니즘인데 "며칠 프로젝트/추가 필요"로 과장 → 「US나 JP나 같은 메커니즘인데 뭘 자꾸 추가적으로 필요하다 이지랄」. 또 dedup 확정 못 한다고 "사람이 눈으로" 제안 → 「뒤진다 가장 확실한 걸로 해」(US도 사람이 안 봤음, 자동이었음).
**How to apply:** 블로커는 진짜 원인(cap/키/도구)만 한 줄. 프레이밍으로 부풀리지 말고 로컬로 되는 최선(firecrawl browser 100행 등) 바로 실행.
