문제("또 X 안 됨")를 던지면 **오늘 그 증상만 해결하는 건 실패다.** 근본 원인까지
파고들어 **앞으로 재발하지 않게** 설계·구현하는 것이 완료 조건.

**Why:** 9/4 JPDash 수집 사고(강한 교정 2연타).
- 메일 폭탄+데이터 안 들어옴 → 처음엔 메일 문구 dedup·오늘치 화면 반영만 하고 보고
  → 「오늘만 해결하는 게 중요한 게 아니라 앞으로 이런 일이 발생하지 않게 하라니까? 이새끼야」
- "메일 폭탄부터 멈춤 / 화면 반영, 뭐부터?" 우선순위 물음 → 「이새끼가 진짜」
  (내가 다 조치할 수 있는데 세은한테 순서를 떠넘긴 게 화근)

**How to apply:**
1. **증상 → 근본 사슬 역추적.** 메일 폭탄(증상) ← catchup이 시드만 복구하고
   build+deploy 안 함(구조 결함) ← 09:20 수집이 RMS 로그인 종속으로 간헐 사망(근본).
   증상 계층에서 멈추지 말고 "왜?"를 데이터/로그/코드로 실측하며 끝까지 내려간다.
2. **재발 방지를 코드/설계에 심는다.** 이번 반창고가 다음에 또 필요 없도록:
   자가복구가 화면 반영까지 완결(build+deploy 자동), 경보 dedup, 실패 원인이
   파일에 남게(수집 태스크 로그 리다이렉트). "다음에 죽어도 스스로 낫고, 죽은
   이유가 남는" 상태가 목표.
3. **내가 조치 가능한 건 우선순위조차 묻지 말고 다 실행.** [[feedback-no-offload-when-i-have-access]]
   [[feedback-yesno-question-stop-at-fact]] 의 연장 — "A부터 할까 B부터 할까"도
   떠넘김이다. 세은 몫은 정책/방향 판단(예: 클라우드 이관 여부)뿐.
4. **막히면 대안 루트로 우회, 포기 X.** OS가 막은 Operational 로그 활성화(관리자도
   거부) → 매달리지 말고 더 나은 대안(수집 태스크 자체 로그)으로 같은 목적 달성.
   [[feedback-coverage-gaps-and-unkillable-pipelines]] 와 같은 결.
